# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Betterlight is a Fabric mod for Minecraft `26.4-snapshot-6` (Java 25, Mojang mappings) that unifies lighting: smooth light on fluids, non-AO models and emitters, per-vertex light on block entities / item frames / paintings, interpolated entity light, front-only light for lit furnaces and jack o'lanterns, and directional face shading moved from the CPU into the shaders. The README is in Spanish; code comments are in English.

## Commands

Gradle crashes with the launcher's JDK (ARM64 daemon dies in `jvm.dll`), so always set `JAVA_HOME` first:

```
export JAVA_HOME=/c/Users/wifft/.jdks/jdk-25.0.4.1+1
./gradlew build          # jar in build/libs; also runs the gametests
./gradlew runClient      # dev client (worlds in run/saves)
./gradlew runGameTest    # headless server gametests (src/gametest, no client code)
./gradlew genSources     # decompiled Minecraft sources for checking signatures
pwsh -File tools/check-overwrites.ps1 [-Update]   # diff docs/vanilla copies against the current MC version
```

There is no linter. The only automated tests are the server gametests in `src/gametest` (`FrontEmitterLightTest`); everything client-side has to be checked in `runClient`. Mixin configs use `defaultRequire = 1`, so an injection that misses its target crashes the game at startup and the log names the mixin.

`.mcsrc/` (Minecraft) and `.mcsrc-fabric/` (Fabric renderer API + Indigo) are gitignored extracted sources, handy for grepping target classes.

## Architecture

Loom `splitEnvironmentSourceSets()`: `src/main` is common code (runs on the server too), `src/client` is client-only. Each has its own mixin config (`betterlight.mixins.json`, `betterlight.client.mixins.json`) — register new mixins there. Interfaces in `duck/` are added to vanilla classes by mixins (methods prefixed `betterlight$`).

**Config** — `BetterlightConfig` holds static volatile flags (read from section-compile and server threads), loaded once from `config/betterlight.properties`, edited in a Betterlight section that `VideoSettingsScreenMixin` appends to Video Settings (saved, and chunks rebuilt if a meshing option changed, when the screen closes). Every feature checks its flag.

**Directional shading in the shader** — The CPU per-face shade is removed (`BlockModelLighterMixin`, `IndigoAoCalculatorMixin`, `IndigoFlatLighterMixin`, `FluidRendererMixin`), and the face normal is written to the vertex instead (`VertexConsumerMixin`, `IndigoQuadViewMixin` honour `shadeDirectionOverride`; fluids get real normals). `RenderPipelinesMixin` swaps `DefaultVertexFormat.BLOCK` for `BetterlightFormats.BLOCK_WITH_NORMAL` and adds the Lighting bind group to terrain/block pipelines. `LightingMixin` grows the Lighting UBO by two vec4 (`CardinalA`/`CardinalB`: per-direction `CardinalLighting` values + a per-face flag, 1 only for the LEVEL entry). The light model is fixed: terrain and block models get per-face shading in the level (`minecraft_terrain_light` in `include/light.glsl`, used by the overridden `terrain.vsh` and `block.vsh`) and vanilla two-light shading elsewhere; entities and items use the unmodified vanilla shaders. Java-side UBO layout and the GLSL `Lighting` block must stay in sync.

**Terrain meshing goes through Indigo, not vanilla** — Fabric API routes block meshing to Indigo's `AltModelBlockRendererImpl`, so block light/AO changes hook Indigo internals (`Indigo*Mixin`, `remap = false`). These break with Fabric API updates and don't apply under Sodium or other renderers. Water still uses vanilla `FluidRenderer`.

**LightField (block entities, item frames)** — `LightField` is a 4×4×4 grid of packed light around a block, camera-relative, sampled trilinearly per vertex (`LightBlend`, shared with `EntityRendererMixin`; cells with zero light are skipped). Flow: cells are captured at extraction (at most once per game tick per object, via `LightCellCache` on `BlockEntity`/`HangingEntity`, `LightCellCacheHolderMixin`; paintings cache their ring the same way) into the render state (`BlockEntityRenderDispatcherMixin` + `BlockEntityRenderStateMixin`, `ItemFrameRendererMixin` + `ItemFrameRenderStateMixin`), then set as the static `LightField.current()` while the renderer submits. `SubmitLightFieldMixin` (one mixin over the four Submit records) copies `current()` into each submit (skipping outline/crumbling submits), and the matching `*FeatureRendererMixin` wraps the vertex buffer with `LightFieldVertexConsumer.wrap`, which replaces each vertex's light. Adding a new submit kind means adding its record to `SubmitLightFieldMixin` (with its exclusion rule) and a FeatureRenderer mixin.

**Front emitters (furnaces, jack o'lanterns)** — A flood fill can't stop light behind a plane, so `BlockLightEngineMixin` (common code) makes them emit nothing in the real light engine; this applies on the server too and is what the gametests cover. On the client, `FrontLightOverlay` runs a per-emitter flood fill that never steps backwards, shaded by line of sight like the directional light (`EmitterBox.shade`). It and `DirectionalLightOverlay` share `EmitterLightOverlay`: fields (`EmitterField`, sparse cells within `RADIUS` of the source) indexed by source section, block/chunk events that only mark emitters dirty (a block change only affects fills that reached it or a neighbour, a chunk load only fills that read it as missing), an `update()` that refills them on a per-frame time budget and then merges the touched sections in batches into a `SectionLightSnapshot` (one byte per block per section, edited as a copy and published immutable for the compile threads), and an `EmitterBox` (lazily read block states of the fill's box, plus the line-of-sight rays). `ClientLevelMixin` feeds both overlays the events, runs their `update()` once per frame from `ClientLevel.update` (profiler sections `betterlight_*`), and installs them through `LevelLightEngineMixin`/`LightEngineMixin` (`BlockLightOverlayTarget`), whose overlay replaces the block engine's `getLightValue` (`BlockLightOverlay.getLightValue(pos, engineLevel)`; the front overlay max-merges, chained after the directional one). `FrontEmitters` (via `EmitterTags`) decides what counts as a front emitter.

**Emitter tags** — `EmitterTags` (common) decides which blocks get emitter light, from `betterlight:shadowed_emitters` and `betterlight:front_emitters` (`src/main/resources/data/betterlight/tags/block/`, extendable by datapacks); unlit states (emission 0) never count, and front emitters also need `HorizontalDirectionalBlock.FACING`. Tags come from the server, so with a server without the mod the client falls back to the bundled `shadowed_emitters.json`, read from the mod jar (`reloadFallback`). `BetterlightClient` listens to `CommonLifecycleEvents.TAGS_LOADED` and, like closing Video Settings after toggling either option, calls `EmitterLightOverlay.rescan()` (every loaded chunk searched again, every field refilled). Front emitters are suppressed in the engine on the server too, so changing their tag or option only fixes stored light when those chunks are relit.

**Shadowed emitters** — Client-only and server-independent (the engine keeps vanilla light, which the server sends): `DirectionalLightOverlay` gives each shadowed emitter a field with its vanilla flood fill V and its shadowed light D (V scaled by line of sight, else indirect light losing `INDIRECT_STEP` per block). Line of sight is 4 vertical sheets of rays per cell from a cube over the emitter's block (nearly the whole block for full-block emitters like glowstone, `isSolidRender`) to the target cell; full opaque blocks and the shapes of blocks the engine occludes by shape (stairs) stop the sheet's two edge rays (each standing for its half), while layers — one full-footprint box from the bottom or top, like snow layers and slabs (`FLOOR`/`CEILING`) — are tested against each of the sheet's 16 rays, so every snow layer in front of the emitter hides a bit more of it; a layered target is judged from its surface. The blocked fraction removes that fraction of the emission (half a slab halves the reach). `getLightValue` takes the vanilla torch light back out of the engine value: if the engine is brighter than the max V another source lights the cell, otherwise it shows max(D, O), O being the other sources' light rebuilt from the engine around the fields in `mergeSections`. Fields are pruned where the engine is `PRUNE_MARGIN` brighter (like the engine's flood fill), which keeps dense torch grids cheap; mistakes there fall back to the vanilla value. Fills wait until the engine has the source's own light (`waitingByChunk`); `ClientPacketListenerMixin` (`applyLightData`) re-merges a chunk's sections when server light arrives and releases its waiting emitters.

**Moving blocks (falling blocks, piston-moved blocks)** — Fabric routes `MovingBlockFeatureRenderer` through Indigo too, but vanilla's `MovingBlockRenderState` is air everywhere but the block itself, so they had no AO. `FallingBlockRendererMixin` and `PistonHeadRendererMixin` capture the 3×3×3 neighbour states at extraction (`NeighborStates`), and `MovingBlockRenderStateMixin` answers `getBlockState` from them. AO is still computed for the whole cell `blockPos`, so it steps when the block crosses a cell.
The AO they cast on the terrain is `MovingBlockShadows`: once per frame (`ClientLevel.update`) it collects the cells of the nearest falling blocks and marks the sections around changed cells dirty; `RenderRegionCacheMixin` copies the cells inside each new `RenderSectionRegion` (main thread, so compile threads read an immutable copy), and `IndigoAoCalculatorMixin` wraps the neighbour `getBlockState` calls in `computeFace` so only AO sees them (culling is unchanged). Piston-moved blocks need no tracking: the AO lookup reads `moving_piston` cells as their moved state. The same wrapper reads extended piston bases as retracted (`extendedPistonAo`), since vanilla only lets full collision shapes cast AO.

**Paintings** — `PaintingRendererMixin` `@Overwrite`s `PaintingRenderer.renderPainting` for per-corner smooth light; the original vanilla method is kept in `docs/vanilla/` for diffing.

## Porting to a new Minecraft version

1. Bump `minecraft_version`, `loader_version`, `loom_version`, `fabric_api_version` in `gradle.properties` (valid versions: https://fabricmc.net/develop or the version branch of FabricMC/fabric).
2. `./gradlew genSources build`; fix signatures against the new sources.
3. `./gradlew runClient` and enter a world (missed injections crash on load).
4. `pwsh -File tools/check-overwrites.ps1`: if a `docs/vanilla` copy (the `@Overwrite`d method or the 3 shaders) changed, port Mojang's change into the mod's version, then refresh the copies with `-Update`.
5. `./gradlew runGameTest`.

Fragile points, most to least: `RenderPipelinesMixin` targets synthetic lambda names (`lambda$terrain$0`, `lambda$block$0`) — verify with `javap -p` on the Loom jar; Indigo mixins (tied to the Fabric API version); the shaders; the `PaintingRenderer.renderPainting` overwrite.
